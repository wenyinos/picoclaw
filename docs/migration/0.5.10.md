# Migrating from 0.3.x / 0.4.x to 0.5.10

0.5.10 upgrades the SQLite memory store to schema v3. There is no configuration change and no manual SQL. The launcher or gateway creates a `VACUUM INTO` backup on first open, then upgrades the schema in place; the data migration runs from `/memory` → “Database migration”, or with `picoclaw memory migrate`.

The one-click path handles v1 and v2 databases:

```text
v1 (0.3.x / early 0.4.x) → v2 (0.4.x / 0.5.0) → v3 (0.5.10)
```

## What changes

- `entries` gains `event_time_precision`, `event_timezone`, `event_time_source`, `valid_from`, `valid_to`, `pinned_core`.
- `sources` becomes an evidence record: `evidence_text`, `confidence`, `user_confirmed`, `message_id`, `extraction_model`, `prompt_version`. The v2 unique key is preserved.
- `memory_relations` stores typed edges; `memory_operations` stores the governance log; `memory_clusters` / `memory_cluster_members` store scene capsules; `memory_summary_versions` is created for future summaries.
- FTS5 indexes `subject/predicate/facet/value/text`. Builds without trigram record `unicode61`; builds without FTS5 record `none` and still open.
- Empty predicates become `待分类`; unknown predicates keep their original value in `attributes.original_predicate`.
- The reference database's nine relationship entries and fourteen `待分类` entries are mapped, the dialogue entry stored as a real profile fact is reclassified, the archived birthday entry is restored, and missing sources are backfilled.
- Orphan sources and broken supersede edges are counted in `meta.v3_dropped_orphan_sources` / `meta.v3_dropped_orphan_supersedes` instead of being dropped silently.

## Upgrade

1. Stop the gateway and launcher.
2. Back up the workspace:
   ```bash
   cp -a ~/.picoclaw/workspace ~/.picoclaw/workspace.backup-$(date +%F)
   ```
3. Start 0.5.10 and open `http://localhost:18800/memory` → “Database migration”.
4. Run the migration. The CLI equivalent is:
   ```bash
   picoclaw memory migrate
   ```
5. Verify:
   ```bash
   sqlite3 ~/.picoclaw/workspace/memory/memory.db "PRAGMA integrity_check;"
   picoclaw memory audit
   ```
   Also check that a public channel cannot see a `fictional/private` persona.

The migration is idempotent. It writes a new `memory/backups/memory.db.bak-*` file each time and keeps the newest two; it never deletes entries.

## Notes

- The v0.4.6 tag remains available; install 0.5.10 to get schema v3 and the launcher migration page.
- Historical 0.3.x → 0.4.0 guide: [0.4.0.md](0.4.0.md).
- `MEMORY.md` is only an import source; the runtime never reads it.
