# PicoClaw 0.7.2

0.7.2 修正 0.7.0/0.7.1 的一个行为缺陷：安装重启后数据库在没有提示的情况下被直接迁移到 v4，用户看不到迁移步骤。现在迁移必须显式执行。

## 修复

- **启动不再自动迁移**：已有 v3 数据库（或缺对象的 v4 库）以故障关闭模式打开。仪表盘和 CLI 仍能打开它，但普通记忆读写会返回 `schema migration required`，直到运行 `picoclaw memory migrate` 或使用 `/memory` → “数据库迁移”。
- **启动不再改动已有库结构**：此前 `Open` 会先创建 v4 空表；现在只有全新空库才直接初始化为 v4。
- **迁移页文案同步为 v3 → v4**：确认框、说明、迁移结果与迁移后建议不再出现“v1/v2 → v3”的旧描述；结果区显示来源行数、已认领域/隔离域与域数量。
- `SourcesRebuilt` 改为迁移后 `sources` 总行数，语义与字段名一致。

## 升级

1. 已由 0.7.0/0.7.1 自动迁移到 v4 的库无需任何操作。
2. 仍是 v3 的库：升级后记忆读写会保持关闭，这是预期行为。打开 `/memory` → “数据库迁移”执行一次，或运行：

   ```sh
   picoclaw memory migrate
   ```

3. 迁移会先做 `VACUUM INTO` 备份，整段事务提交；重复执行零变更。
4. `forget-ledger.db` 与 `memory.db` 同目录，必须一起备份。

## 验证

- `go test -tags 'goolm stdjson' ./pkg/memstore`：v3 库打开后 pending、读写被拒绝、显式迁移后恢复、缺对象自愈需再次显式迁移。
- 前端 `pnpm run lint` 与 `pnpm run build` 通过。

## 已知边界

- 外部 LLM 抽取、向量/语义召回仍未接线，保持默认关闭。
- JSONL 清理只做内容精确匹配；无法验证时报告 partial。
- Seahorse 侧逐条清理仍缺少接口，报告 partial。
