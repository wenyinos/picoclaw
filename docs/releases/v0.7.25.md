# PicoClaw 0.7.25

0.7.25 是一次记忆完整性与恢复门禁修复版本。主库 Schema 仍为 v4，不改变记忆条目结构；修复重点是 Replay 越权、恢复状态机、来源证据、并发安全和文档契约。

## 背景

0.7.20 已关闭大量原始安全缺陷，但后续对当前源码和真实快照复核时发现：

- 通用 Replay 仍会执行已标记 `blocked` 的 intent，且不重新校验逐目标 revision。
- Seahorse assembler 的双重检查懒初始化存在可重复 data race。
- 群聊可通过显式 `realm` 覆盖 `IncludeFic=false`。
- cleanup job 的 `cancelled/blocked` 状态没有恢复入口，内存中的聚合结果缺少持久 per-locator 回执。
- origin event 主要存在于 Schema，生产写路径没有形成完整来源链。
- owner review/persona 路径仍绕过统一审计，LIKE 通配符和预算溢出指标未正确处理。

## 安全与治理

- **Replay 门禁**：`blocked` intent 永不执行；新 manifest v2 保存逐目标 domain 与 expected revision。旧 manifest 只有在来源 HMAC 与当前条目正文匹配时才可执行。
- **默认预览**：API Replay 默认 dry-run，`confirm=true` 才执行；CLI `replay-forget` 默认预览，`--yes` 才执行。Web 先展示 eligible/blocked/unapproved 数量。
- **多目标原子性**：一个 intent 内任一目标 revision/domain/内容证明冲突时，整个 intent 不删除任何条目。
- **群聊 realm 隔离**：群聊/公开聊天只允许 `real`；显式 fictional/work 返回 `ErrRealmNotAllowed`。Service 与 Store SQL 都执行交集，低层调用不能扩大权限。
- **导入收口**：HTTP `POST /api/memory/import` 返回 410，不再接受任意宿主机路径；CLI 导入经 `MemoryService`，默认 `private`、`pending`、`legacy_unassigned`。
- **统一审计**：review、persona、状态变化、Replay、任务重排和来源撤回记录 actor、request ID 与 reason code；persona 与状态变更递增 entry revision。
- **来源撤回**：新增受控 `MarkOriginUnavailable`。没有其他可用来源的条目变为 `unsupported/stale`，相关摘要失效，不自动删除事实。

## 恢复与清理

- **恢复门禁**：启动时同步执行安全对账；存在 pending/blocked intent、pending/running/blocked/cancelled cleanup、缺默认域或孤儿 domain 时，长期记忆故障关闭。普通聊天可以继续，但不会注入或写入长期记忆。
- **独立回执**：账本新增 `forget_receipts`，按 backend + locator 记录 `pending/running/removed/verified_absent/unavailable/outcome_unknown/blocked`；不保存正文。
- **真实结果**：缺后端回执、后端错误或无法核验时不会标记 done。前一次运行已到达后端但回执未完成的 locator，在本次确认不存在时记录 `verified_absent`，不冒充“本次删除”。
- **任务恢复**：新增 `requeue-job --yes` 与 `POST /api/memory/jobs/{id}/requeue`。为 blocked/cancelled/failed cleanup 创建新后继任务，旧行保留为 `superseded`，不会改写历史。
- **CLI 反馈**：`memory cleanup` 在 partial、unknown、blocked、cancelled、pending backlog 或恢复未就绪时返回非零。
- **默认域修复**：显式 `memory repair` 会先备份主库与账本，再只补已知的 `legacy_unassigned` 行；不猜 owner，不修改其他域。

## 来源与运行时

- **origin event 生产接线**：自动抽取在入站边界生成稳定 `oe_` 身份；memory 工具写路径按可信 session/message/action 生成来源。模型不能提供或覆盖来源根。
- **多来源保留**：同一事实来自不同消息时合并条目但保留多个 `sources`；来源唯一键不再被空 origin 折叠。
- **持久抽取任务**：自动抽取改为 `memory_jobs` 中的 durable 引用，只保存来源 keyed digest、session 和 origin，不保存聊天正文；worker 从已持久化会话中重新读取并校验原文。
- **自动抽取边界**：子代理内部轮次、群聊/公开/未知 ChatKind、异步 follow-up 和被排除渠道不进入长期画像。
- **Seahorse 并发**：assembler/compaction 改为构造期初始化，移除无同步双重检查；race 门禁恢复。
- **关闭路径死锁**：Channel Manager `StopAll` 不再持写锁等待 outbound dispatcher，避免并发 outbound 时停止挂起。
- **清理重试**：legacy 摘要每次 retry 前重新检查 egress；Seahorse 摘要缺可信 session 时 fail closed，不再退回 default agent。

## 检索、预算与接口

- **LIKE 字面量**：转义 `%`、`_` 和反斜杠，查询不再被通配符扩大。
- **预算指标**：`FixedUsage.OverflowTokens/CoreOverflow` 真实赋值；核心 boundary 不静默丢弃，溢出可见。
- **上下文估算**：context usage 使用最近一次实际渲染的 fixed+retrieval token，不再无条件加入整份配置预算。
- **OpenAPI**：新增 `docs/reference/memory-v4.openapi.yaml`，覆盖当前 40 条记忆 HTTP 路径。
- **恢复页面**：`/memory` 治理页显示 readiness、blocked/cancelled/inert cleanup、任务回执摘要，并提供后继任务入口。

## 验证

本版本发布前执行并得到以下结果：

- `go build -tags 'goolm stdjson' ./...`：通过。
- `go test -tags 'goolm stdjson' ./... -count=1 -timeout=900s`：**93 个包通过，20 个包无测试文件，0 失败**。
- `CGO_ENABLED=1 go test -race ... ./pkg/memstore ./pkg/memory ./pkg/seahorse ./pkg/agent`：四个包全部通过，无 data race 报告。
- 前端 `pnpm run lint`：0 error、8 个既有 Hook warning；`pnpm run build`：通过。
- `make lint-docs`：通过；OpenAPI YAML 解析为 3.1.0，覆盖当前全部 40 条记忆路径。

```sh
go build -tags 'goolm stdjson' ./...
go test -tags 'goolm stdjson' ./... -count=1 -timeout=900s
CGO_ENABLED=1 go test -race -tags 'goolm stdjson' \
  ./pkg/memstore ./pkg/memory ./pkg/seahorse ./pkg/agent \
  -count=1 -timeout=900s
cd web/frontend && pnpm run lint && pnpm run build
```

新增回归覆盖：

- blocked/未批准/修订变化/多目标 Replay 冲突；
- 旧 manifest digest proof；
- 恢复门禁、cancelled 后继任务、分后端回执、outcome_unknown、prior-running → verified_absent；
- origin event 幂等、多来源保留、来源撤回支持状态；
- 群聊显式 realm 与低层 Store 交集；
- LIKE 通配符、boundary 溢出；
- durable extraction job 不含正文并可完成；
- 前端恢复状态与 Replay 预览。

## 升级

- 主库 Schema 无变化，仍为 v4；账本内部新增表/列，启动时自动创建，旧账本只读兼容。
- 覆盖二进制并重启 launcher/gateway。无需新增配置字段。
- 启动后先运行：

```sh
picoclaw memory recovery-status
picoclaw memory cleanup
```

- 若显示 blocked/cancelled cleanup，先用 `GET /api/memory/jobs` 或 dashboard 检查原因，再执行 `picoclaw memory requeue-job <job-id> --yes` 创建后继任务；不要直接把数据库状态改回 pending。
- HTTP 导入已禁用；旧 workspace 导入改用 `picoclaw memory import --from <workspace>`。
- 旧数据没有 origin/root/actor 时继续报告 unknown/legacy，不自动补造。

## 已知边界

- 完整 `MemoryUseManifest` 持久派生污点链、临时无记忆会话和发送前撤权 epoch 仍未完成。
- 外部 LLM 抽取、embedding/向量检索、MMR 和主动投递调度仍保持关闭。
- 完整多域 relationship/capsule、每 Agent 独立 Seahorse Engine、长文分块和时间抽取仍未接线。
- 来源编辑/撤回目前依靠受控 owner API；渠道未提供编辑/撤回通知时不能实时同步。
- 历史 HMAC 密钥轮换、未知旧 key 的跨代匹配，以及每后端恢复代际仍无独立密钥管理闭环。
- 参考快照中的历史 177 次无账本 forget、117 条无 root 来源和 2 条 cancelled job 不会被自动修复；需要 owner 显式审计/后继动作。
- V4 配置中尚未接线的开关即使存在配置文件，也不代表能力已生效。
